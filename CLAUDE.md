# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repository Is

ShiftTemplates is a dual-purpose repository: it contains a **dotnet new** project template (`shift`) and item template (`shiftentity`), and the template content itself doubles as a **sample project** (StockPlusPlus) used during Shift Framework development.

There are two solution files serving different purposes:
- **`ShiftTemplates.sln`** — for template packaging and the Builder tool
- **`content/Framework Project/StockPlusPlus.sln`** — the sample project / framework development

## Build & Run

```bash
# Build entire solution (from repo root)
dotnet build

# Build sample project
dotnet build "content/Framework Project/StockPlusPlus.sln"

# Run the API
dotnet run --project "content/Framework Project/StockPlusPlus.API"

# Apply EF Core migrations (from Package Manager Console or CLI)
dotnet ef database update --project "content/Framework Project/StockPlusPlus.Data" --startup-project "content/Framework Project/StockPlusPlus.API"
```

## Tests

```bash
# Run sample project tests (xUnit 3)
dotnet test "content/Framework Project/StockPlusPlus.Test"

# Run Blazor component tests (bunit)
dotnet test "content/Framework Project/StockPlusPlus.Web.Tests"
```

## Template Builder

The `ShiftTemplates.Builder` console app automates template development workflow:

```bash
# Full workflow: update versions, pack, install template, create test project
dotnet run --project ShiftTemplates.Builder

# Individual steps
dotnet run --project ShiftTemplates.Builder -- --update-template-versions --skip-template-install --skip-project
dotnet run --project ShiftTemplates.Builder -- --skip-project
```

The Builder: (1) reads `ShiftFrameworkGlobalSettings.props` and updates template.json with current versions, (2) packs and installs the template via `dotnet new install`, (3) creates a test project using `dotnet new shift`.

## Architecture

### Development Mode vs Package Mode

Controlled by `ShiftFrameworkGlobalSettings.props` at the repo root. When `shiftFrameworkDevelopmentMode` is defined and sibling framework repos are cloned with the correct folder structure, projects use **local project references** instead of NuGet packages. This file is excluded from the template output.

Required sibling repos for development mode: `ShiftEntity`, `ShiftBlazor`, `ShiftIdentity`, `TypeAuth`, `AzureFunctionsAspNetCoreAuthorization`, `ShiftFrameworkTestingTools`, `ShiftFrameworkLocalization`, `ShiftMapper`.

`ShiftMapper` (https://github.com/ShiftSoftware/ShiftMapper) is referenced by `StockPlusPlus.Data` — the runtime library as a normal project reference and `ShiftMapper.Generator` as an analyzer (the source-generator half of the single `ShiftSoftware.ShiftMapper` package; the package also carries `ShiftMapper.CodeFixes`, which is IDE-only and is not wired in dev mode, matching ShiftMapper's own sample) — and by four framework projects: since 2026-09-15 `ShiftEntity.CosmosDbReplication` (library only — it is the mapping fallback for Cosmos replication, see below) and `ShiftIdentity.Data` (library + generator, which carries the identity replication maps as a profile), and since 2026-09-19 `ShiftEntity.Core` and `ShiftEntity.EFCore` (library + generator: the repository-mapping rules pack, the markers and the framework tag maps — the repository triple maps through ShiftMapper since Stage 3 of the plan below). Every sibling that references the runtime library uses the TypeAuth pattern: `ProjectReference` when the checkout exists, `PackageReference` at `$(ShiftMapperVersion)` otherwise. ShiftMapper pins `Microsoft.Extensions.DependencyInjection.Abstractions` 10.0.11, so any project that references that package directly AND reaches ShiftMapper must sit at 10.0.11 or restore fails with NU1605. **The pipeline clones it anonymously like every other sibling, so the GitHub repository must be public before a `release*` tag is built** — the clone is unconditional because the sample build needs the checkout (the package is only ever published from this pipeline). And because the framework packages now depend on it, the first release after this must be `release-all` (or `release-shiftmapper` first), never a lone `release-framework`.

**Cosmos replication maps through ShiftMapper.** The mapping delegate on `Replicate` / `UpdateReference` / `UpdatePropertyReference` (both pipelines in `ShiftEntity.CosmosDbReplication`) is optional; a call site that omits it maps through the host's registered `IMapper` (ShiftMapper's run-time door — renamed from `IShiftMapper` on 2026-09-17), resolved by `ReplicationMapper.cs` ONCE per registered action and ABOVE the row loop, with the pair checked via `CanMap` — a missing mapper or pair throws out of the run rather than surfacing as permanently-dirty rows under a clean watermark (which is how the old AutoMapper fallback failed; never move the resolution inside the per-row catch). **ShiftMapper's model (since its 2026-09-17 commits `125abd4` + `1514014`):** a mapper class (`ShiftMapperBase`) is ONLY a place to write `CreateMap`s — nothing is generated onto it, it need not be `partial`, nothing injects it. The generator writes ONE generated class per assembly holding every map from every mapper class in the project AND every mapper class the referenced packages declare; the typed methods (`mapper.Map<BrandDto>(x)`, `MapToBrandDto`, `ProjectTo`) are extension methods on `Mapper`, the one object application code injects; `IMapper` (5 members, `CanMap` included) is the door for library code that cannot name the host's types, and `Mapper` implements it explicitly. `services.AddShiftMapper()` registers the CALLING ASSEMBLY's generated mapper (nothing is named) plus `Mapper`/`IMapper` over every generated mapper any call registered, dispatching each pair to the first that declares it, the application's own first; a repeat call from the same assembly is a no-op in the registry. `o.AddMapper<T>()` only matters under `MapperDiscovery.LocalAndRegistered`/`Registered` and is SM0046 under the default `All`; `CompositeShiftMapper` and public `IncludeMapper` are gone. ShiftIdentity's 19 replication pairs are declared in `ShiftIdentity.Data/Replication/ShiftIdentityReplicationMapper.cs` (a plain `ShiftMapperBase`; rules would go in a `ShiftMapperConversions` pack, of which identity has none); `SetUpAllIdentityReplications` (Dashboard.AspNetCore), `ReplicateAllAsync` (AzureFunctions) and the template's `UtilityController.ReplicateAll` pass no delegates. **The mapper is registered by the identity registrations themselves** — `AddShiftIdentityDashboard<TDbContext>()` (API side) and the Functions worker's `AddShiftIdentity(issuer, key)` (catch-up side) both call `AddShiftIdentityReplicationMapper()` — so the template hosts carry no line for it; it cannot ride on `SetUpAllIdentityReplications` because the trigger's options callback runs per scope over an already-built container. That call is just `services.AddShiftMapper(o => o.Lifetime = lifetime)` made FROM ShiftIdentity.Data, so it registers that assembly's generated mapper; keep it an inline lambda, not the generic short form, because `Assembly.GetCallingAssembly()` is not inlining-safe across the identity registrations. Its idempotency is ShiftMapper's own (no guard of its own any more). A host with a generator of its own writes NOTHING to get the pairs: they are in its generated mapper because it references the package, and `Mapper` answers from the host's first; re-declaring one of the 19 pairs in a second mapper class is refused (SM0042). A host that wires identity replication without either identity registration calls `AddShiftIdentityReplicationMapper()` itself. `StockPlusPlus.Data` carries a generated mapper of its own for the same reason (it references ShiftIdentity.Data with the generator attached) but never registers it — the sample makes no `AddShiftMapper` call — so at run time the door is ShiftIdentity.Data's. The documents are pinned by the 24 frozen goldens in `StockPlusPlus.Test/Tests/ReplicationMappingParityTests.cs` (mapping through `Mapper.Create(typeof(ShiftIdentityReplicationMapper).Assembly)` held as `IMapper` — the package's own generated mapper through the run-time door) plus `IdentityReplicationMapperRegistrationTests.cs` (which asserts the container holds the generated type, one `Mapper` and one `IMapper`, never the mapper class, and cross-checks the pairs against the `ShiftMapperDeclaredMap` metadata by `DeclaredBy`); the mapper's transcription rules (ignore `ID` on every map, ternaries for navigation reads, `"0"` for a key behind a null navigation, `BranchID` ignored on the merge maps) are documented in the mapper itself. The repository triple (`IShiftEntityMapper`) maps THROUGH ShiftMapper since Stage 3 of the plan below (2026-09-19); the old ShiftEntity generator was deleted in Stage 4 (2026-09-20) — `ShiftEntity.SourceGenerator` no longer exists, and the one ShiftEntity analyzer left is `ShiftEntity.Analyzers` (SHENT001).

### Sample Project Structure (StockPlusPlus)

- **API** — ASP.NET Core Web API (.NET 10). Controllers, DbContext, identity integration
- **Data** — EF Core entities, repositories, migrations. Uses ShiftEntity.EFCore patterns
- **Shared** — DTOs, enums, TypeAuth action trees (permission definitions)

- **Web.Tests** — bunit Blazor component tests

### Template System

Template config lives in `content/Framework Project/.template.config/template.json`:
- **sourceName**: `StockPlusPlus` — replaced with user's project name during `dotnet new shift`
- Key parameters: `includeSampleApp` (bool), `shiftIdentityHostingType` (Internal/External), `addFunctions` (bool), `addTest` (bool)
- Conditional compilation via `#if` directives tied to template symbols (e.g., `includeSampleApp`, `internalShiftIdentityHosting`)
- The item template at `content/ShiftEntity/` scaffolds a full entity (DTO, entity class, repository, controller, Blazor page)

### Framework Version Management

`ShiftFrameworkGlobalSettings.props` defines `ShiftFrameworkVersion`, `TypeAuthVersion`, `AzureFunctionsAspNetCoreAuthorizationVersion` and `ShiftMapperVersion`. The Builder's `UpdateTemplateVersions` reads these and writes them into `template.json` so newly created projects get correct package versions. The last three are standalone: each sibling repo imports this props file — from the `ShiftTemplates` folder and from `s`, the pipeline's checkout directory, with the path relative to the importing file (`..\..\` from a csproj one level below the repo root, as in TypeAuth; `..\` from `ShiftMapper`'s repo-root `Directory.Build.props`) — and sets its `<Version>` from its own entry, so those packages move independently of the framework version. `ShiftMapper` keeps a fallback number in that props file for standalone clones; the published number is always the one here.

## CI/CD

Azure DevOps pipeline (`azure-pipeline.yml`) triggers on `release*` tags. It clones all framework sibling repos, builds everything, runs tests, then packs and publishes NuGet packages. **Test projects come in two tiers.** A project the pipeline runs by default finishes in seconds and needs nothing outside the process: no SQL Server, no Cosmos emulator, no real-clock waits. Anything slower lives in a separate `*.LongRunning` test project, or is a whole project of that kind such as `ShiftMapper.Generator.Tests`, and runs on the pipeline only when the tag name contains `with-long-running-tests`, for example `release-framework-with-long-running-tests` or `release-all-with-long-running-tests`; locally, run such a project on purpose from Test Explorer. On `release-all` and `release-framework` tags only, before anything is packed, `.pipelines/identity-checks.steps.yml` builds the fast identity test projects once in Release and runs two gates with `--no-build`: `identity-policy` (all of `ShiftIdentity.Tests`: database-free policy and token tests, plus the shared fixtures that `ShiftIdentity.Tests.LongRunning`, `StockPlusPlus.Test` and the sample API's development hosts build on; no SQL connection is passed, so a SQL-backed test that lands there fails) and `identity-ui` (all of `ShiftIdentity.Blazor.Tests`, bunit). The other tags publish no identity package and skip the whole block at template-expansion time. With the long-running tag the template also starts a disposable SQL Server container and runs `identity-long-running` (all of `ShiftIdentity.Tests.LongRunning`: every SQL-backed identity test and the real-clock response-floor evidence, about six minutes on a hosted agent) and `identity-consumer-contract` (`Category=IdentityConsumer` in `StockPlusPlus.Test`, SQL-backed). The `Category` traits (`Policy`, `Sql`, `Http`, `Ui`) stay on the identity classes as descriptions; only `IdentityConsumer` is still used as a filter. The ShiftMapper generator suite (484 Roslyn compilations) is likewise run only with the long-running tag; ShiftMapper's own GitHub workflow runs it on every push. Tag naming controls what gets published: `release-all`, `release-framework`, `release-typeauth`, `release-aspNetCore-authorization`, `release-shiftmapper`. `release-all` publishes every group; the specific tags publish only their own. The ShiftMapper group runs `ShiftMapper.Tests` (and `ShiftMapper.Generator.Tests` only with the long-running tag), packs `ShiftSoftware.ShiftMapper` (one package carrying the library and the generator) into its own staging folder, verifies both halves are inside the `.nupkg`, and pushes with `-SkipDuplicate` so a `release-all` after a `release-shiftmapper` of the same version does not fail.

The nesting depth is `Nested = 10` on the framework's markers, capped per repository (or per entity in `ConfigureRepository`) with `o.Mapping(m => m.Nested(n))` — the ONLY thing `Mapping(...)` accepts, read at build time, recorded at run time on `ShiftRepositoryOptions.NestedMappingDepth`; a member is dropped in a mapper class, `CreateMap<Product, ProductDTO>().ForMember(d => d.X, opt => opt.Ignore())` (one map per direction it exists in; declare the write map as `.ReverseMap()` of the view map so entity-only members stay the quiet SM0006). There are no mapping attributes, and nothing about what a member maps from is written in a repository.

**Conversions are ShiftMapper's, plus the framework's pack.** ShiftMapper's built-in conversions cover the scalars (numeric, `bool`, dates/times, `Guid`, enums ↔ `string`, enums ↔ numbers, numeric ↔ numeric; invariant culture) and collections (element and container type independently); `ShiftEntity.Core/Mapping/ShiftEntityConversions.cs` adds the framework's rules — ID/IdempotencyKey/Tags/Revisions ignored as destinations, `ReloadAfterSave`/audit members both ways, the `ShiftEntitySelectDTO` select convention (`{Member}ID` + `{Member}.{NameOf}`, `Name` fallback, element half), files ↔ JSON, and `string? → long` for a required foreign key through `MappingHelpers.ToRequiredLong` (a 400 `ShiftEntityException` naming the field). A value ShiftMapper cannot convert on a write surfaces as the same 400 (`ShiftMapperEntityMapper` translates `ShiftMapperConversionException`). A member with no query form leaves the LIST projection with SM0030 rather than failing at query time.

**Soft delete is NOT the mapper's concern.** It is enforced by the repository and the OData layer — `ApplyDefaultSoftDeleteFilter` in `ShiftEntity.Web/Extensions/IQueryableExtensions.cs` and `ShiftEntityCrudHandler`. Both cover ROOT rows only, so children composed deep inside a payload are not filtered by anything — and that is the INTENDED behaviour, not a gap: Step B10 of the removal plan was DROPPED on 2026-08-23 for exactly that reason, and `Tests/TaggingTests.cs::Product_DeletedTag_IsStillReturnedOnBothTheViewAndTheList` pins it so it does not come back. If root-level filtering ever needs extending, it belongs in the repository/EF layer, not in generated mapping code.

Attribute-driven endpoints can also take a mapper (iteration §20 in the planning doc). Alongside `[ShiftEntityEndpoint<…>]` / `[ShiftEntityEndpoint<…, TRepository>]`, there are `[ShiftEntityEndpointWithMapper<…, TMapper>]` / `[ShiftEntitySecureEndpointWithMapper<…, TActionTree, TMapper>]` where `TMapper : class, IShiftEntityMapper` (a non-generic marker; the exact `(entity,list,view)` triple is validated at discovery). A mapper keeps the built-in repository but replaces the automatic ShiftMapper maps. Sample: `StockPlusPlus.Data/Entities/Country.cs` exposes `api/country` (automatic) and `api/countrymapped` (`Mappers/CountryMapper.cs` + the distinct `Shared/DTOs/CountryMappedDTO.cs` — a distinct DTO is REQUIRED because the mapper is keyed by DTO type). ### The ShiftEntity analyzer (SHENT001)

The old mapping generator's diagnostics (SHENGEN001–011) are gone with it; ShiftMapper's SM00xx diagnostics describe the maps now (SM0047 an explicit `CreateMap` replacing an automatic map, SM0049 a write map rebuilding a child collection, SM0042 two mapper classes declaring one pair, SM0030 a list member with no query form, …). The ONE ShiftEntity rule that was never about mapping lives in `ShiftEntity.Analyzers/RepositoryConfigurationAnalyzer.cs`, a plain `DiagnosticAnalyzer` packed into `ShiftSoftware.ShiftEntity` under `analyzers/dotnet/cs` (dev mode: `OutputItemType="Analyzer"` project references from `ShiftIdentity.Data.csproj` and `StockPlusPlus.Data.csproj`, because analyzer project references do not flow transitively).

**SHENT001** (Error; the former SHENGEN006) fires when an entity declares `IConfiguresShiftRepository<E, L, V>` while a repository for the SAME triple passes an options builder to its base constructor — the builder means the repository configures itself and takes over, so the entity's `ConfigureRepository` never runs and nothing fails at runtime. Fix: move the config into the repository's builder, or drop the builder. Detection only fires on a certainty — it requires a DIRECT `ShiftRepository<,,,>` base and needs EVERY constructor reaching base to pass a non-null builder, so an intermediate base class or a single builder-less constructor stays silent rather than break a build on a guess. There is no opt-out attribute.

Tests: `ShiftEntity.Tests/Analyzers/RepositoryConfigurationAnalyzerTests.cs` — drives the analyzer in-process over a hand-built compilation (`CompilationWithAnalyzers`; the analyzer is a plain ProjectReference in that project, deliberately NOT an analyzer). The "silent" cases are as much the contract as the firing one.

When working on mapping-related changes, always check the planning doc for current iteration status before starting.
