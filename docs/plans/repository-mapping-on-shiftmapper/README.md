**Goal in one sentence:** the mapping between a repository's entity and its DTOs — nested children included —
is generated by **ShiftMapper**, automatically, from the repository's type arguments; the programmer writes
no attribute and no class for the plain case, configures in the repository or in a mapper class using
ShiftMapper's own vocabulary, can use those maps anywhere; and ShiftEntity's own generator, registry,
fluent builder and mapping attributes are deleted.

## 1. Where things stand today

Every `ShiftRepository<DB, TEntity, TListDTO, TViewDTO>` needs four mapping methods:

| Method | What it does | Runs where |
|---|---|---|
| `MapToView` | entity → view/upsert DTO | in memory |
| `MapToEntity` | DTO → the tracked entity (update in place) | in memory |
| `MapToList` | `IQueryable<Entity>` → `IQueryable<ListDTO>` | **in SQL** — one `Select` EF translates |
| `CopyEntity` | entity → entity (refresh a tracked row) | in memory |

A programmer gets those four methods from one of three doors:

1. **Source-generated** (the default) — `ShiftEntity.SourceGenerator` (2,662 lines) finds every repository and
   every `[ShiftEntityEndpoint<…>]`, writes the four methods with ShiftEntity's conventions, discovers nested
   child pairs (`InvoiceLine ↔ InvoiceLineDTO`), and registers everything in `ShiftEntityMapperRegistry`.
   Customized through `UseGeneratedMapper(map => map.ForList(…))` in the repository, or a
   `[ShiftEntityMapper] partial class` with a `Configure` hook. Three attributes belong to it:
   `[ShiftEntityMapper]`, `[ShiftEntityMapperIgnore]`, `[ShiftEntityMapperMaxDepth]`, plus the
   `UseGeneratedMapper = true` property on the endpoint attributes.
2. **Repository override** — the repository overrides the four virtual methods by hand (`ProductRepository`).
3. **Hand-written mapper** — a class implementing `IShiftEntityMapper<E, L, V>` (`CountryMapper`), plugged
   through `UseMapper(...)`, DI, or `[ShiftEntitySecureEndpointWithMapper<…, TMapper>]`.

Meanwhile the framework has adopted **ShiftMapper** — a general compile-time mapper with its own generator,
a rules-pack system for frameworks, and `IMapper` for library code. Cosmos replication and ShiftIdentity's
replication maps already run on it. So the framework carries **two** mapping generators that do overlapping
work: ShiftEntity's, which knows the framework's conventions but nothing else, and ShiftMapper's, which
knows mapping deeply but nothing about repositories.

## 2. What we want

1. **ShiftMapper generates the four repository maps, automatically.** From the repository's type arguments
   and from the endpoint attributes — the programmer writes nothing for the plain case, exactly as today.
2. **Nested children are automatic too** (`InvoiceDTO.InvoiceLines`, `InvoiceListDTO.InvoiceLines[].Product`).
3. **No attributes for mapping.** The three ShiftEntity mapping attributes and the `UseGeneratedMapper = true`
   property are deleted and **nothing replaces them with another attribute**. The framework's own rules are code
   in a rules pack.
4. **Configuration in the repository still works**, written in ShiftMapper's own vocabulary
   (`o.Mapping(m => m.List.ForMember(...))`), and flows into the generated map.
5. **A mapper class overrides the repository.** `CreateMap<E, L>()` in any `ShiftMapperBase` class replaces
   the automatic map for that pair; every customization for that pair lives there, and the repository's
   configuration for it is ignored (the build says so).
6. **The maps work anywhere.** Not only inside the repository: any service, any project that references the
   data project, any library through `IMapper` — see §6.
7. **The framework's conventions move into ShiftMapper rules**: `FK ↔ ShiftEntitySelectDTO`, `string ↔
   List<ShiftFileDTO>`, audit fields, "`ID` is never written from a request", Tags owned by the tagging
   pipeline, and the rest of [`03-coverage.md`](03-coverage.md).
8. **The gaps are filled** — chiefly a **collection** of `ShiftEntitySelectDTO` (`List<ShiftEntitySelectDTO>
   Departments`), which today is a hand-written `ForView` + `ForList` in every repository that has one.
9. **The old generator is deleted**, with the registry, the fluent builder, the pair-mapper interface, the
   attributes and the `SHENGEN` diagnostics; ShiftMapper's diagnostics take over saying what is not mapped.

## 3. Three facts that decide the design

### Fact 1 — a generator cannot read another generator's output

Every source generator in a build runs over the **original** source at the same time. Generator A's output is
never an input to generator B. So —

> "ShiftEntity's generator writes a `ShiftMapperBase` class with `CreateMap<Invoice, InvoiceDTO>()` for every
> repository, and ShiftMapper's generator compiles it"

— **does not work** inside one project. (It *can* be made to work one project away, by writing ShiftMapper's
declaration metadata into `Data.dll` for the API's generator to read — the way a package's maps travel.
That was considered and rejected: a repository living in the host project would silently get no maps, the
warnings about a repository would land in the API's build with no line to click, and ShiftEntity would have
to write ShiftMapper's metadata format byte-exact. See [`02-open-decisions.md`](02-open-decisions.md) Q9.)

The consequence: **whatever finds the repositories has to be inside ShiftMapper's generator**, and ShiftMapper
must stay ignorant of ShiftEntity. ShiftMapper's generator already reads *attributes on referenced types*
(that is how a package's maps and packs cross an assembly). The one signal it needs is on ShiftEntity's
**own base class**, not on anything the programmer writes: *"a class deriving from this generic type declares
maps between its type arguments."* The programmer's repository is then automatic — the same way the old
generator recognised the name `ShiftRepository`, only now ShiftMapper recognises a marker ShiftEntity carries.
One generator, no second layer, no programmer attribute.

### Fact 2 — most of what the old generator does by hand is already a ShiftMapper rule

| Old generator does… | ShiftMapper already has… |
|---|---|
| `long`/`Guid`/enum ↔ `string`, `int?` → `int`, `List` ↔ `HashSet`, invariant culture | the built-in conversion table (`docs/conversions.md`) |
| `FK ↔ ShiftEntitySelectDTO` with `Text` from `[ShiftEntityKeyAndName]` | **member conventions** — the README's `SelectDto` example is this exact rule, `{Member}ID` + `{Member}.{NameOf}`, and the write direction is derived |
| `string ↔ List<ShiftFileDTO>` via `MappingHelpers` | `CreateConversion<string?, List<ShiftFileDTO>>(memory: …)` in a pack (no query form → SM0030, same as today's "unmapped in list") |
| nested child pairs composed into view/entity/list | nested maps, composed in memory **and inside one EF projection** |
| unmapped-member warnings (SHENGEN004/007), asymmetry (008), ambiguity (011), conditional config (005/009) | SM0001, SM0006, SM0007, SM0035 |
| "the shape is baked at build time, the expressions arrive at run time" (`ShiftMapperBuilder` + `InvokeView`) | the same split, for package mappers: shape as metadata, `MapFrom` trees from the class's constructor |

What the old generator has and ShiftMapper does **not**: automatic discovery from repositories (Fact 1),
automatic *nested* declaration (ShiftMapper makes a missing nested map an error, SM0011, on purpose),
configuration written somewhere other than a mapper class, pack-level "ignore this framework member", and a
convention for a *collection* of shaped members. Those are the ShiftMapper work in this plan (§7). Everything
else is configuration.

### Fact 3 — ShiftMapper keeps one map per pair per assembly

Today each repository gets its **own instance** of the generated mapper, so two repositories on the same
`(entity, list, view)` triple could be customized differently. Under ShiftMapper a pair has **one map per
assembly**. The repository can still configure it (§5) — but only one repository per pair may, and a mapper
class for the pair wins over any repository. Two repositories that want different shapes need different DTOs,
which is already the framework's rule for `WithMapper` endpoints and how the sample is built. See Q1.

## 4. The design in one picture

```
 ShiftEntity (package — the programmer never sees this part)     Your project (e.g. StockPlusPlus.Data)
 ────────────────────────────────────────────────────────────     ─────────────────────────────────────
 marker on ShiftRepository<DB, TEntity, TList, TView>  ─closed by─▶  class InvoiceRepository
 marker on ShiftEntityEndpoint<TList, TView>                            : ShiftRepository<DB, Invoice, InvoiceListDTO, InvoiceDTO>
   "declare TEntity↔TView, TEntity→TList, TEntity→TEntity,            {
    nest 10 deep, apply ShiftEntityConversions"                            base(db, o => o.Mapping(m =>                ◀── optional
                                                                               m.List.ForMember(d => d.Total, …)))     configuration,
 ShiftEntityConversions (rules pack, code not attributes)              }                                               ShiftMapper vocabulary
   • IgnoreMember<ShiftEntityBase>(e => e.ID, Destination)                     │
   • IgnoreMember<IShiftEntityTaggable>(e => e.Tags, Destination)              │  ShiftMapper's generator reads the marker
   • SelectDTO member convention (single + collection)                         │  and the o.Mapping(...) lambda
   • string ↔ List<ShiftFileDTO>                                               ▼
                                                                    CreateMap<Invoice, InvoiceDTO>().ReverseMap()           ┐ automatic
 ShiftEntityFrameworkMaps (mapper class)                            CreateMap<Invoice, InvoiceListDTO>()                    │ maps,
   • Tag → TagDTO, Tag → TagListDTO                                   .ForMember(d => d.Total, …)   ← from o.Mapping        │ nested
                                                                    CreateMap<Invoice, Invoice>()                           │ ones
                                                                    CreateMap<InvoiceLine, InvoiceLineDTO>().ReverseMap()   │ included
                                                                    CreateMap<InvoiceLine, InvoiceLineListDTO>()            ┘
                                                                               │
                                                                               │  a mapper class of yours declaring a pair
                                                                               │  REPLACES the automatic map for that pair
                                                                               ▼
                                                                    one generated mapper for the assembly
                                                                               │
 ShiftRepository (EFCore)                                                      │ at run time, through IMapper
   MapToView   = mapper.Map<E, V>(entity)                          ◀───────────┘ (and through Mapper anywhere else — §6)
   MapToEntity = mapper.Map<V, E>(dto, existing)
   MapToList   = mapper.ProjectTo<E, L>(query)
   CopyEntity  = mapper.Map<E, E>(source, target)
```

**Precedence for one pair, top wins:**

```
1. a mapper class declaring the pair       — in this project; else the nearest package that declares it
2. the repository's o.Mapping(...) for it  — one repository per pair
3. the automatic map from the type arguments, with the framework's rules pack
```

Plus the two doors that do not change: overriding the four virtual methods in the repository, and a
hand-written `IShiftEntityMapper`.

**Resolution order in the repository** (unchanged in spirit, one link replaced):
`UseMapper(...)` → an `IShiftEntityMapper<E,L,V>` registered in DI → **ShiftMapper's `IMapper`, if it
`CanMap` the pairs** → nothing, and the mapping methods throw (caught at startup by
`ShiftEntityMapperValidation`, exactly as today).

## 5. What the programmer writes — before and after

### Zero code (Country, ProductCategory, `api/country-generated`)

```csharp
// Before
public CountryRepository(DB db) : base(db, x => x.UseGeneratedMapper()) { }

// After — the repository's type arguments ARE the declaration
public CountryRepository(DB db) : base(db) { }
```

```csharp
// Before
[ShiftEntitySecureEndpoint<CountryGeneratedDTO, CountryGeneratedDTO, StockPlusPlusActionTree>("api/country-generated", …, UseGeneratedMapper = true)]

// After — the property is gone; the attribute declares the maps by itself, always
[ShiftEntitySecureEndpoint<CountryGeneratedDTO, CountryGeneratedDTO, StockPlusPlusActionTree>("api/country-generated", …)]
```

### Configure in the repository — same place as today, ShiftMapper's vocabulary

`m.View`, `m.Entity`, `m.List`, `m.Copy` are ShiftMapper's own `MapExpression<,>` for the four automatic maps,
so `ForMember` / `Ignore` / `MapFrom` / `AfterMap` are the same calls you would write in a mapper class.

```csharp
public class InvoiceRepository : ShiftRepository<DB, Invoice, InvoiceListDTO, InvoiceDTO>
{
    public InvoiceRepository(DB db, IHashIdService hashIds, IShiftEntityMappingContext ctx) : base(db, o =>
    {
        o.IncludeRelatedEntitiesWithFindAsync(x => x.Include(i => i.InvoiceLines));

        o.Mapping(m =>
        {
            m.List.ForMember(d => d.Total, opt => opt.MapFrom(e => e.InvoiceLines.Sum(l => l.Price)));  // runs in SQL

            m.Entity.ForMember(e => e.InvoiceNo, opt => opt.Ignore())
                    .AfterMap((dto, entity) =>
                    {
                        entity.ManualReference = entity.ManualReference?.Trim();
                        if (ctx.ActionType == ActionTypes.Insert) entity.ReleaseDate = null;
                    });

            m.View.ForMember(d => d.PublicKey, opt => opt.MapFrom(e => hashIds.Encode(e.ID)));           // a captured service is fine

            m.Nested(2);   // optional: cap automatic nesting for this repository (default 10)
        });
    })
    { }
}
```

The same `Mapping(...)` is available on `context.Options` inside an entity's
`IConfiguresShiftRepository.ConfigureRepository` (the built-in-repository case).

**How it works** — the split ShiftMapper already uses for package mappers: at **build time** the generator
reads the lambda for its *shape* (which members are customized or ignored, whether there is an `AfterMap`),
exactly as it reads a mapper class's constructor, so every diagnostic still fires; at **run time** the lambda
runs when the repository is constructed, as today, and its expressions go into the customization store the
generated map reads. Two rules follow: the lambda must be inline and unconditional (SM0035 — the same rule
SHENGEN005 enforces today), and one repository per pair may configure it (Q2).

### Customize in a mapper class — overrides the repository for that pair

```csharp
// Before — ShiftEntity's own fluent vocabulary, on a partial class the generator fills
[ShiftEntityMapper]
public partial class ProductBrandMapper : IShiftEntityMapper<ProductBrand, ProductBrandListDTO, ProductBrandDTO>
{
    partial void Configure(ShiftMapperBuilder<ProductBrand, ProductBrandListDTO, ProductBrandDTO> map)
        => map.ForList(d => d.Code, entity => entity.Code ?? "(No Code)");

    public ProductBrand MapToEntity(ProductBrandDTO dto, ProductBrand existing, MappingContext context = default)
    {
        existing = MapToEntityGenerated(dto, existing, context);
        existing.Code = existing.Code?.Trim();
        return existing;
    }
}

// After — an ordinary class, no attribute, nothing partial, nothing registered.
// Declaring a pair REPLACES the automatic map for that pair — and anything the repository's
// o.Mapping(...) said about that pair is ignored (the build says so). The two pairs not
// mentioned here (entity → view, entity → entity) stay automatic.
public class ProductBrandMapper : ShiftMapperBase
{
    public ProductBrandMapper()
    {
        CreateMap<ProductBrand, ProductBrandListDTO>()
            .ForMember(d => d.Code, opt => opt.MapFrom(e => e.Code ?? "(No Code)"));

        CreateMap<ProductBrandDTO, ProductBrand>()
            .AfterMap((dto, entity) => entity.Code = entity.Code?.Trim());
    }
}
```

The framework's rules (select DTOs, files, `ID` never written, …) still apply to a map you declare yourself:
they are a pack, not something baked into the automatic map.

### Ignore a member — no attribute

```csharp
// Before: map.Ignore(d => d.Secret)  /  [ShiftEntityMapperIgnore] on the property
// After, in the repository:   m.View.ForMember(d => d.Secret, opt => opt.Ignore());
//        or in a mapper class: CreateMap<Product, ProductDTO>().ForMember(d => d.Secret, opt => opt.Ignore());
```

One call per direction the member exists in — usually one or two.

### Customize a nested child once, for every parent that nests it

```csharp
// Before — inside each parent's config:
option.UseGeneratedMapper(map => map
    .ForListChildren(d => d.InvoiceLines, e => e.InvoiceLines, line =>
        line.ForChild(l => l.Product, il => il.Product)));

// After — nothing, for the plain case: children nest automatically. To customize the child,
// declare its pair once; every parent that nests it picks it up, in memory and in SQL.
public class InvoiceLineMapper : ShiftMapperBase
{
    public InvoiceLineMapper() =>
        CreateMap<InvoiceLine, InvoiceLineListDTO>()
            .ForMember(d => d.Description, opt => opt.MapFrom(l => l.Description.Trim()));
}
```

### The two doors that do not change

- **Repository override** (`ProductRepository`): still overrides the four virtual methods, still uses
  `MappingHelpers` (`ToSelectDTO`, `MapBaseFields`, `ShallowCopyTo`). Untouched.
- **Hand-written `IShiftEntityMapper`** (`CountryMapper`, `[…WithMapper<…, CountryMapper>]`): untouched.

### One line in the host

```csharp
// Program.cs (API, Functions, tests) — registers this assembly's generated mapper,
// which carries every map from every referenced project and package.
builder.Services.AddShiftMapper();
```

`RegisterShiftRepositories(...)` also registers the generated mapper of every assembly it scans (Q8), so a
host that only scans its data assembly is covered with no extra line. A host that has neither fails **at
startup** with a message naming the line, not on the first request.

## 6. The maps work anywhere, not only in the repository

The automatic maps are ordinary maps in the assembly's generated mapper. So:

```csharp
// In the data project, or ANY project that references it — typed methods, compile-checked:
public class InvoiceSummaryService(Mapper mapper, DB db)
{
    public InvoiceDTO Read(Invoice invoice)          => mapper.MapToInvoiceDTO(invoice);        // or mapper.Map<InvoiceDTO>(invoice)
    public Task<List<InvoiceListDTO>> Page()         => db.Invoices.ProjectTo<InvoiceListDTO>(mapper).Take(50).ToListAsync();
    public Invoice Apply(InvoiceDTO dto, Invoice row) => mapper.Map(dto, row);                  // update in place
}

// In library code that cannot name the types — IMapper, the run-time door:
IMapper mapper = ...;
if (mapper.CanMap(typeof(TEntity), typeof(TDto))) dto = mapper.Map<TEntity, TDto>(entity);
```

What that gives, without anyone writing anything:

- **Same map everywhere.** A repository's `o.Mapping(...)` customization is part of the map, so the service
  above gets `Total` too. (ShiftMapper builds the repository from DI the first time the map is used outside
  it, as it builds a mapper class from DI today — the one design cost, see Q3.)
- **Cosmos replication** already maps through `IMapper` when a call site passes no delegate; an entity's
  automatic maps are now candidates there as well.
- **Every referencing project** (API, Functions, tests) has the same typed methods, because a project's
  generated mapper carries every map from every referenced project and package.
- **A host can override a package's pair** (an app reshaping a ShiftIdentity DTO) with a mapper class of its
  own — nearest wins, and the build says so (SM0027).

## 7. What ShiftMapper gains — six general features, none of which mentions ShiftEntity

| # | Feature | Why ShiftEntity needs it |
|---|---|---|
| **M1** | **Implicit maps from a marked generic type.** A marker on an open generic class or attribute class: "every closing type declares maps between these type arguments", with `Reverse`, `Nested`, `Rules`, `Flattening`. Generated as a mapper class that travels like any package mapper. | Fact 1 — automatic discovery of repositories and endpoint attributes. The marker lives in ShiftEntity; nobody else writes it. |
| **M2** | **Nested declaration** (`Nested = n`): every (class, class) member pair with no declared map gets an implicit map, recursively, to depth *n*; cycles stop with an Info; a member a convention claims is not nested; `m.Nested(n)` in the configuration surface overrides the depth. | Today's automatic pair mappers and `MaxDepth`. |
| **M3** | **A configuration surface on the closing type.** The marker names a surface type whose properties are the `MapExpression<,>` of the implicit maps; a lambda handed to it (`o.Mapping(m => …)`) is read at build time for shape, and the closing type (the repository) holds the customizations at run time — constructed from DI on first use, like a mapper class. A mapper class declaring the pair replaces it (Info; Warning if the surface also configured it). Two closing types configuring one pair is an error. | "Configuration in the repository flows to ShiftMapper." |
| **M4** | **Pack-level member ignore rules**: `IgnoreMember<TDeclaring>(x => x.Member, MemberRole)` in a `ShiftMapperConversions` pack — applies to every map whose source/destination is assignable to `TDeclaring` (interfaces included). | "`ID` is never written from a request", `ReloadAfterSave`, `AuditFieldsAreSet`, `Tags` on write, `Revisions` on read — as code in the framework's pack, with no attribute anywhere. |
| **M5** | **Collection member conventions**: a `CreateMemberConvention<T>()` that also applies to `IEnumerable<T>` members, filling each element from the matching element of the source collection. | The `List<ShiftEntitySelectDTO>` gap. |
| **M6** | An Info diagnostic when an **update** map (`Map(source, destination)`) rebuilds a nested collection. | Successor of SHENGEN010 — the one warning that stops a silent orphan/duplicate on save. |

Everything else is ShiftMapper as it is today. Details and samples per feature are in [`01-steps.md`](01-steps.md).

## 8. What ShiftEntity gains and loses

**Gains** (all small, all configuration):
- `ShiftEntityConversions : ShiftMapperConversions` — the rules pack: the member ignores, the select DTO
  convention (single and collection), the files conversions. Shared by the framework's registration.
- `ShiftEntityFrameworkMaps : ShiftMapperBase` — the framework-owned pairs (`Tag → TagDTO`, `Tag → TagListDTO`).
- The marker on `ShiftRepository<,,,>` and the endpoint attributes (not the `WithMapper` ones), and the
  configuration surface `ShiftEntityMapping<E, L, V>` behind `ShiftRepositoryOptions.Mapping(...)`.
- `ShiftRepository` maps through `IMapper`; `IShiftEntityMappingContext` (scoped) carries `ActionType`.
- `ShiftEntityMapperValidation` asks `IMapper.CanMap` instead of the registry.

**Loses** (deleted outright — and **no attribute replaces any of them**):

| Deleted | What to write instead |
|---|---|
| `[ShiftEntityMapper]` partial mapper class | an ordinary `ShiftMapperBase` class declaring the pairs it customizes |
| `[ShiftEntityMapperIgnore]` | `ForMember(d => d.X, opt => opt.Ignore())` in `o.Mapping(...)` or a mapper class |
| `[ShiftEntityMapperMaxDepth(n)]` | `m.Nested(n)` in `o.Mapping(...)` |
| `ShiftEntityMapperDefaults` | the marker's defaults inside ShiftEntity |
| `UseGeneratedMapper = true` on the endpoint attributes | nothing — always automatic |
| `UseGeneratedMapper()` / `UseGeneratedMapper(map => …)` | nothing / `o.Mapping(m => …)` |
| `ShiftMapperBuilder`, `ShiftChildMapperBuilder`, `IShiftMapperConfigurable`, `IShiftObjectMapper` | ShiftMapper's own `MapExpression<,>` and nested maps |
| `ShiftEntityMapperRegistry`, `GeneratedMapperFactory`, module initializers | the generated mapper, registered by `AddShiftMapper()` |
| `ShiftEntity.SourceGenerator` (whole project), all eleven `SHENGEN` diagnostics, `SelectWithTags` | ShiftMapper's generator and `SM` rules |

`[ShiftEntityKeyAndName]` is **not** a mapping attribute (it says which member of an entity is its display
name, and the UI uses it too); the select DTO convention reads it, and it stays.

**Keeps**: `IShiftEntityMapper<E,L,V>` and `MappingContext` (hand-written mappers), `MappingHelpers`
(hand-written mappers and repository overrides), the `WithMapper` endpoint attributes, the four virtual
methods on `ShiftRepository`.

## 9. How the work is ordered, and why

1. **Freeze the oracle first.** Record what today's generator produces for every triple in the sample and in
   ShiftIdentity, as goldens — the same lesson as the AutoMapper removal: once the old generator is gone there
   is nothing to diff against.
2. **Build the ShiftMapper features** (M1–M6), each with generator tests, released as ShiftMapper `0.3.0`.
3. **Add the ShiftEntity side without removing anything**: pack, framework maps, marker, configuration
   surface, and the `IMapper` link in the repository *behind* the old generated mapper — so nothing changes
   yet, but both mappers exist on the same host and the goldens can be diffed against ShiftMapper's output.
4. **Flip**: `IMapper` ahead of the registry; migrate the sample, the item template and ShiftIdentity's
   repositories; make every golden pass. (Done; the goldens were then removed — the comparison was their job.)
5. **Delete** the old generator, the attributes and everything attached; update CLAUDE.md, the docs, the
   pipeline notes. (Done 2026-09-20, in the same unreleased window as the flip — see Q7.)

Steps are in [`01-steps.md`](01-steps.md).
